## 문제 1. 파드 오토스케일링 (27회차)

### (a) `resources` 선행 필수 이유

**묻는 것:** HPA 전에 Deployment `resources` 설정이 반드시 선행돼야 하는 이유 · 리소스 제한이 없으면 파드 오토스케일이 무의미해지는 이유 · 그 상황에선 어떤 종류의 오토스케일링을 해야 하는지.

**답:**

HPA는 resource.requests 를 기반으로 사용률을 계산함으로 선생되어야함
리소스 제한이 없으면 계산이 안되기때문에 무의미하다. 리소스 제한이 없는 상황에서는 어떤 오토스케일링이 필요한지는 모르겠다.

### (b) HPA · Deployment · metrics-server 역할 구분

**묻는 것:** 세 요소의 역할 구분 · HPA에 없는 기능은 무엇이고 누가 대신하는지 · metrics-server를 커스텀할 필요가 없는 이유.

**답:**

HPA는 특정 Deployment에 자원에 오토스케일링을 담당한다.
Deployment는 자원 생성 및 설정과 관련된 매니페스트이다.
metrics-server는 Deployment에 의해 생성된 파드에 매트릭을 수집하고 지속적으로 보고해주는 역할

HPA에 없는 기능은 모르겠다

metrics-server는 클러스터내에 설치시 자동으로 cpu/메모리를 감시함으로 딱히 손댈 필요없다.

### (c) HPA 값 결정 근거

**묻는 것:** 이 주문 서비스의 `minReplicas`/`maxReplicas`/`averageUtilization` 값과 근거. 다음 셋 모두 반영:
- 임계치 50% 테스트에서 파드가 3대까지만 늘고 CPU가 43%로 내려간 이유(지표의 정의)
- "파드 생성 중에도 CPU가 튀니 임계치·리소스 limit을 여유롭게" 라는 말의 의미
- Deployment `replicas`와 HPA `minReplicas`가 다를 때 무엇이 우선하는지 · 실무에서 둘을 어떻게 관리할지

**답:**

1 부하로 인해 파드 개수가 늘어났고 그로인해 최신 적용되서 푱균치가 내려갔다.
2. 파드 생성하고 서버를 띄우는 부트스트랩 과정에서도 리소스가 어느정도 사용되니 여유롭지 않으면 부팅 시점에 오토스케일러가 동작하는 현상을 방지하기 위해 여유롭게 둔다.
3. HPA를 우선으로 한다. 그럼으로 실무에서는 두 값을 동일하게 둔다.

## 문제 2. 인스턴스 오토스케일링과 Pod 권한 (28~30회차)

### (a) HPA만 있을 때 maxReplicas를 올리면

**묻는 것:** HPA만 적용된 채 `maxReplicas`를 10·20으로 올려 부하를 주면 생기는 현상 · 그 원인과 파드가 놓이는 상태 · "노드를 관리하는 주체는 EKS가 아니다"의 의미 · cluster-autoscaler가 무엇을 감지해 누구에게 무엇을 요청하는 프로그램인지.

**답:**

노드 리소스에 한계가 생겨 파드가 할당받지 못하고 PENDING 상태가 된다. EKS는 Kubernetes 컨트롤 플레인을 관리할 뿐 워커 노드 증설을 자동으로 수행하지 않으므로, AWS ASG와 Cluster Autoscaler를 구성해야 한다. Cluster Autoscaler는 스케줄할 수 없는 Pending 파드를 감지하고, 이를 수용할 수 있도록 AWS ASG에 EC2 워커 노드 증설을 요청한다.

### (b) **핵심** — cluster-autoscaler Pod에 IAM 역할 부여가 복잡한 이유

**묻는 것:** 다음 흐름으로 설명:
- AWS가 역할을 부여하는 기본 엔터티는 무엇이고 왜 Pod는 그 단위가 아닌지
- EKS의 OIDC 공급자 URL을 ID 제공업체로 등록하면 무엇이 가능해지는지
- 대상에 `sts.amazonaws.com`을 넣는 이유와 STS의 역할
- Pod → STS → 역할 → ASG 요청 흐름
- 신뢰 정책의 `"<OIDC>:sub": "system:serviceaccount:kube-system:cluster-autoscaler"` 조건이 없으면 생기는 문제 · 이 조건이 Deployment/ServiceAccount 설정의 무엇과 맞물리는지

**답:**

AWS IAM 역할은 EC2 같은 AWS 서비스에 주는건데 pod는 AWS 서비스가 아니라서 바로 역할을 못준다.

그래서 EKS에서 제공해주는 OIDC를 IAM에 등록하고 cluster-autoscaler pod가 신뢰할수 있는 대상으로 인식하게 만든다. STS는 임시 권한을 주는 서비스로 알고있다.

pod가 STS를 통해 역할을 받아서 ASG에 EC2 늘려달라고 요청하는 흐름이다.

`sub` 조건은 cluster-autoscaler 서비스어카운트만 이 역할을 쓰게 막는 조건같다. 이 부분은 정확히 잘 모르겠다.

### (c) **핸즈온** — 노드가 늘지 않고 파드가 `Pending`

**묻는 것:** ① 이 파드 진단에 `kubectl logs`가 쓸모없는 이유와 대신 쓸 명령·확인할 내용 · ② 강의에서 실제로 발견한 **설정 누락**이 무엇이고 어디서 고쳤는지 · ③ 노드 증설은 즉시인데 감축은 10~30분 뒤인 비대칭이 의도된 설계인 이유.

**답:**

Pending은 파드가 아직 실행이 안됐으니까 logs는 볼게 없을것 같다. `kubectl describe pod`로 events를 보고 cpu나 memory 부족한지 확인한다.

강의에서는 노드 그룹 최대 개수가 2라서 안늘어났고 EKS 노드 그룹에서 최대를 3으로 바꿨다.

늘리는건 부하를 바로 처리해야되고 줄이는건 바로 줄이면 다시 늘려야할수 있어서 늦게 줄이는것 같다.

## 문제 3. ArgoCD GitOps 도입 (31회차)

### (a) GitHub 소스 기준 확신 가능 영역 / 불가능 영역

**묻는 것:** 지금 아키텍처에서 "GitHub 소스 기준으로 돌고 있다고 확신할 수 있는 영역"과 "확신할 수 없는 영역" 구분 및 차이가 생기는 이유 · 팀원 4명이 `kubectl` 권한을 가진 상태에서 누군가 로컬에서 `replicas`를 3으로 바꿔 apply했을 때의 문제를 **안정성**과 **이력 관리**로 나눠 서술.

**답:**

왜 깃헙 소스 기준으로 돌고 있는지 확신 할수 없냐면 개발자가 임의로 로컬에서 Deployment를 수정해서 kubectl apply 하면 깃헙이랑 다르게 적용되기 때문. 이렇게 팀원(개발자)가 임의로 replicas를 수정하고 깃헙에 푸시&PR을 안하면 다른 사람이 이 변경을 인지못해 이력관리 허술해 지고 임의로 수정했기때문에 안정성또한 떨어진다.

### (b) `prune` / `selfHeal` 구분 · ArgoCD가 하지 않는 일

**묻는 것:** `prune: true`와 `selfHeal: true`가 각각 켜는 동작 구분 · 강의가 "첨언"으로 강조한 **ArgoCD가 하지 않는 일** 한 가지와 그것이 남기는 운영상 사각지대.

**답:**

prune은 deployment 에 변경을 사항을 보고 삭제되는게 있으면 삭제시키는 옵션
selftHeal은 github과 리소스 싱크를 맞추는 옵션
그리고 ArgoCD는 깃헙에 올라와있지않은 리소스는 체크와 싱크를 못한다.

### (c) `Application` 자원의 필요성 · 개수 · Pending 재apply 여부

**묻는 것:** 핵심 컴포넌트만 apply하면 부족해 `Application`을 따로 만들어야 하는 이유 · 네임스페이스 3개 운영 팀이라면 Application 몇 개가 필요한지와 이유 · argocd 네임스페이스 파드가 `Pending`일 때 노드 추가 후 실패한 자원을 다시 apply해야 하는가와 그 이유(마스터 노드/워커 노드 역할 분담으로 설명).

**답:**

네임스페이스를 3개 운영한다면 Application도 3개가 필요하다. Application 하나가 특정 레포를 바라보고 있기때문

argocd 네임스페이스의 파드가 Pending이었다가 노드를 추가했다면 실패한 자원을 다시 apply할 필요는 없다. 마스터노드가 워커노드 증설 후 자동으로 상태가 바뀔 것이기 때문

## 문제 4. ArgoCD 퍼블릭 대시보드와 Ingress 분기 (32회차)

### (a) **핵심** — ArgoCD 서버에 Ingress + HTTPS를 붙이면 생기는 문제

**묻는 것:** 순서대로 ① Ingress가 사용자 요청 암호문에 대해 하는 일 · ② 우리 Spring 서버 Pod에서는 문제되지 않았던 이유 · ③ "암호문을 그대로 Pod에 넘기면 되지 않나"가 불가능한 이유(Ingress 구현 기준) · ④ 어떤 설정을 어디에 추가했고 그것이 보안상 위협이 되지 않는 이유.

**답:**

1. 암호화된 요청 복호화
2. Spring 서버는 8080으로 들어온요청을 따로 복호화하거나 하지 않는다
3. Ingress가 이미 복호화한걸 다시 암호화해서 ArgoCD에 못넘겨준다 Https -> https
4. ArgoCD가 복호화하는 옵션을 ArgoCD 매니페스트에서 제거함

### (b) 두 Ingress의 동일 `ADDRESS`와 도메인 기반 분기

**묻는 것:** `argo.<도메인>`과 `server.<도메인>` 두 Ingress의 `ADDRESS`가 동일한 이유 · 하나의 로드밸런서로 도메인 분기가 이뤄지는 구조를 ingress-controller → Ingress → Service → Pod 흐름으로 설명 · 서브도메인을 하나 더 추가하면 무엇을 몇 세트 더 만들어야 하는지(Route 53 레코드·인증서 포함).

**답:**

둘 다 ingress-controller가 만든 하나의 네트워크 로드밸런서를 공유하기 때문에 동일함.
서브 도메인 추가시 Route53 레코드와 인증서만 추가적으로 작업하면 된다.

## 문제 5. 프로메테우스 · 노드 익스포터 · 그라파나 (33~34회차)

### (a) 모니터링 대상의 차이 · 노드 익스포터를 DaemonSet으로 배포하는 이유

**묻는 것:** HPA·ArgoCD로 봐 온 것과 프로메테우스/그라파나로 새로 보게 되는 것의 **모니터링 대상 차이** · 노드 익스포터를 `Deployment`가 아니라 `DaemonSet`으로 배포하는 이유(이 워크로드의 성격과 함께).

**답:**

HPA나 ArgoCD는 파드나 배포 상태를 보는거고 프로메테우스, 그라파나는 노드 cpu나 메모리같은 자원도 보는것 같다.

노드 익스포터는 각 노드의 정보를 봐야해서 모든 노드에 하나씩 떠야한다. 그래서 Deployment가 아니라 DaemonSet을 쓴다.

### (b) **핵심** — Service 대신 `hostPort`, 그리고 `__address__` 포트 replace

**묻는 것:** 노드 익스포터에 Service를 쓰면 안 되는 이유(**Service의 기본 동작 방식** 근거) · `hostPort`가 무엇을 가능하게 하는지 · 프로메테우스 config에서 `__address__` 기본 포트 `10250`을 `9100`으로 `replace`하는 설정이 이 결정과 어떻게 **쌍을 이루는지**.

**답:**

Service는 여러 pod중 하나로 라운드로빈해서 노드별로 정보를 다 못가져올수 있다.

hostPort는 노드의 9100 포트로 직접 접근할수 있게 하는거다. 그래서 프로메테우스도 기본 10250 포트가 아니라 9100으로 바꿔서 노드 익스포터에 접근한다.

### (c) `/proc`·`/sys`·`/` readOnly 마운트 · 그라파나 데이터 소스 URL

**묻는 것:** 세 경로를 `readOnly`로 마운트하는 이유(파드는 자기만의 파일 경로를 갖는데 왜 호스트 경로를 가져와야 하는지 · 세 경로가 각각 담는 정보) · 그라파나 데이터 소스 URL에 무엇을 입력하는지(포트 포함)와 그 주소로 프로메테우스에 도달할 수 있는 이유.

**답:**

파드는 자기 내부 파일만 볼수있어서 노드 정보를 보려면 호스트 경로를 마운트해야된다. `/proc`은 cpu, 메모리 같은 정보고 `/sys`는 하드웨어 정보, `/`는 디스크 정보이다.

읽기만 하면되서 readOnly로 한다.

그라파나에는 `http://prometheus-service:9090`을 넣는다. 같은 클러스터 내부 service라서 접근됨

## 문제 6. 통합: 세 가지를 한꺼번에 켰을 때 (종합)

> 전제(참고): HPA(최대 10대) + cluster-autoscaler 상시 유지, GitHub `deployment.yaml`에 `replicas: 2` 선언, ArgoCD가 그 경로를 `prune: true, selfHeal: true`로 관리.

### (a) 세 설정을 그대로 켜면

**묻는 것:** 강의에서 배운 **각 자원의 동작 규칙만으로** 추론해, 어느 쪽이 이기고 그 결과 피크에 무슨 일이 생기는지까지 서술. (+ ⚠ 범위 밖: 이 충돌을 해소하는 실무적 방법(매니페스트에서 `replicas` 제거, ArgoCD가 특정 필드 차이를 무시하도록 설정 등) / 몰라도 됨)

**답:**

HPA가 부하때문에 파드를 5개로 늘려도 ArgoCD selfHeal이 github에 있는 replicas 2개로 다시 바꿀것 같다.

그러면 피크때 필요한 파드가 줄어서 문제가 생길수 있다. 이 충돌을 어떻게 해결하는지는 모르겠다.
