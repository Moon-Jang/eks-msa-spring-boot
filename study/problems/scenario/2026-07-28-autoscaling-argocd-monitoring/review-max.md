## 문제 1. 파드 오토스케일링 (27회차) — 17/20

### (a) HPA 이전에 `resources` 선행이 필요한 이유 — 충족 (6/6)

**제출 요지**
> "pod는 해당 ec2의 자원을 끝까지 할당하여 사용하기 때문에 pod를 늘릴수 있는 ec2 리소스 자체가
> 부족하기때문에 pod 오토스케일링이 의미가 없어진다. 그 상황에서는 노드(ec2)를 스케일 업 또는
> 스케일 아웃을 해야함."

**맞은 점**
- "파드가 EC2 자원을 끝까지 점유 → 파드를 늘릴 여유 자원 자체가 없음 → 노드 스케일 업/아웃으로
  전환"까지 루브릭이 요구한 논리 사슬이 완전함. 만점.

### (b) HPA · Deployment · metrics-server 역할 구분 — 부분 충족 (5/7)

**제출 요지**
> "HPA에 없는 기능은 모니터링과 파드를 직접 만들고 지우는 기능... 모니터링은 metric-server가
> 파드의 CPU, 메모리 사용량을 수집... 파드를 만들고 지우는 기능은 Deployment가 replica 설정값을
> 통해 실제 파드 갯수를 유지함."

**맞은 점**
- 세 요소의 역할 분담(HPA=판단, metrics-server=수집, Deployment=개수 유지)은 정확.

**놓친 점**
- 문제가 명시적으로 물은 "**metrics-server를 왜 커스텀할 필요가 없는지**" 답변이 없다.
  설치되면 클러스터의 HPA를 알아서 찾아 그 대상 파드를 모니터링하므로 우리 사정에 맞출 게 없고,
  반면 HPA는 대상/임계치가 전부 우리 사정이라 반드시 커스텀해야 한다는 대조가 빠졌다.

### (c) 이 주문 서비스의 HPA 값 설계와 근거 — 부분 충족 (6/7)

**제출 요지**
> "minReplicas: 2 / maxReplicas: 4 / averageUtilization: 70 or 80... c-1: 파드 전체의 평균 CPU
> 사용률이기 때문. c-2: 스프링부트를 실행시키는 초기에 CPU가 확 튐... c-3: HPA를 우선한다.
> 동일하게 맞추는게 제일 좋다."

**맞은 점**
- 임계치를 실무 기준 70~80으로 잡은 것은 루브릭 가점 사항.
- 스파이크 원인을 "스프링부트 초기 기동 시 CPU가 튐"으로 구체화한 것, HPA 우선 + 둘을 맞춰
  관리한다는 결론 모두 정확.

**놓친 점**
- c-1에서 "평균이라서"까지는 맞았으나, "3대로 분산되면 같은 총 부하에 파드당 평균이 임계치
  아래로 내려가므로 더 늘릴 이유가 없음 = **설정 오류가 아닌 정상 동작**"이라는 결론 문장이
  빠졌다. 실무에서 "HPA가 고장났다"는 오탐 이슈를 걸러내는 핵심 문장이다.
- maxReplicas 4의 근거(노드 용량 대비)도 서술이 없다.

## 문제 2. 인스턴스 오토스케일링과 Pod 권한 (28~30회차) — 16/22

### (a) HPA만 켠 상태에서 `maxReplicas`를 올리면 — 충족 (5/6)

**제출 요지**
> "노드의 리소스가 허용될때 까지만 늘어나고 그 이후로는 pending 상태... HPA는 파드가 몇개
> 필요한지만 알고 요청보내기 때문... AWS의 오토스케일링 그룹이 관리하기때문...
> [cluster-autoscaler는] 리소스 부족을 감지하여 오토스케일링그룹에 노드 수를 증가/감소 하라고
> 요청보내는 프로그램."

**맞은 점**
- Pending 발생 메커니즘, ASG가 노드 관리 주체, autoscaler = "감지 후 ASG에 요청하는 프로그램"
  모두 정확. 흔한 오답("autoscaler가 직접 EC2를 만든다")을 피함.

### (b) **핵심** — cluster-autoscaler Pod에 IAM 역할 부여가 복잡한 이유 — 부분 충족 (6/10)

**제출 요지**
> "b-1: AWS에서 제공되는 리소스를 기본단위로 함. pod는 aws의 기본 리소스가 아니기 때문.
> b-2: 역할부여가 가능해짐. b-3: sts는 임시 보안자격증명을 발급하는 서비스. b-4: 파드가 STS로
> 임시 보안자격증명을 요청... 그 역할로 ASG에 EC2 증가/감소 요청을 보냄. b-5: 잘 모르겠음."

**맞은 점**
- b-1(AWS는 자사 리소스 단위로 역할 부여, Pod는 해당 없음)과 b-4(Pod→STS 임시 자격증명→역할로
  ASG에 증감 요청) 정확 — 흔한 오답("Pod에 Role 직접 부착")을 피함.

**놓친 점**
- b-2: "역할부여가 가능해짐"은 결과만 쓴 것. **OIDC URL이 'EKS(=AWS 자원)가 보증하는 신원'이
  되어 클러스터 내부 요소가 IAM 세계로 들어올 통로가 열린다**는 매개 논리가 빠졌다.
- b-3: STS 정의는 맞았으나 신뢰 정책의 대상(Principal)에 `sts.amazonaws.com`을 넣는 이유 —
  이 OIDC 신원의 주체가 STS를 통해 `AssumeRoleWithWebIdentity`를 호출할 수 있게 허용하는
  설정 — 를 안 썼다.
- b-5 미답(−2): `sub` 조건이 없으면 **같은 클러스터의 아무 ServiceAccount나 이 Role을 assume해
  ASG/EC2 권한을 갖는 과도한 권한 문제**가 생기고, 이 조건이 SA의 annotation
  (`eks.amazonaws.com/role-arn`) + Deployment의 `serviceAccountName`과 이름/네임스페이스 단위로
  정확히 맞물린다는 게 이 문항의 핵심 배점 지점이었다. IRSA 장애의 대부분이 이 3점(신뢰 정책
  sub ↔ SA 이름 ↔ serviceAccountName) 불일치에서 나오므로 실무 임팩트가 큰 누락.

### (c) **핸즈온** — 노드가 안 늘고 파드가 `Pending` — 충족 (5/6)

**제출 요지**
> "pending 상태일땐 컨테이너가 아직 생성되지 않았기 때문에 logs 명령어가 쓸모가 없음.
> kubectl describe pod... 오토스케일링 그룹의 최대값을 2 -> 3으로 수정... 감축은 진짜 필요 없는
> 노드가 맞는지 충분한 시간을 갖고 확인한 뒤 실행하는게 좋기때문."

**맞은 점**
- logs 무용 이유(컨테이너 미생성) + describe 사용, ASG 최대값 2→3 수정 모두 정확.

**놓친 점(경미)**
- describe로 **무엇을 확인하는지**(Events의 `0/N nodes are available: Insufficient cpu/memory`)
  까지 물었는데 명령만 썼다.
- 증설이 즉시인 이유("부하는 지금 당장 대응해야 함")의 대칭 서술이 약하다.

## 문제 3. ArgoCD GitOps 도입 (31회차) — 15/20

### (a) GitHub 소스 기준이라 확신 가능/불가능한 영역 — 충족 (7/7)

**제출 요지**
> "확신할 수 있는 영역: github 액션에서 실행되는 구간... 확신할 수 없는 영역: 쿠버네티스 리소스
> 상태 및 설정 파일... 안정성 관점: 다른 팀원들은 깃헙에 있는 replicas 설정을 보고... 판단을
> 할텐데 애초에 판단 근거 자체가 전부 틀려버려짐. 이력 관리 관점: 누가, 언제, 왜 바꿨는지 모름.
> 롤백도 쉽게 할 수 없음."

**맞은 점**
- 만점. 특히 안정성 관점을 "팀원들의 판단 근거(GitHub 선언) 자체가 틀려버린다"로 표현한 것은
  루브릭의 "합의와 어긋난 인프라"를 본질적으로 짚은 좋은 답. "롤백도 쉽게 못 한다"는 루브릭에
  없는 타당한 추가 근거로 인정.

### (b) `prune` / `selfHeal` · ArgoCD가 하지 않는 일 — 부분 충족 (3/6)

**제출 요지**
> "prune: 깃에 없으면 클러스터에서도 없앰. selfHeal: 깃에 선언된 리소스가 클러스터와 다르면
> 깃 설정으로 맞춤."

**맞은 점**
- 두 옵션의 정의는 정확하고 간결.

**놓친 점**
- 문항의 절반인 "**ArgoCD가 하지 않는 일**"이 통째로 미답이다. GitHub에 선언되지 않은 리소스를
  누가 클러스터에 새로 만들어도 ArgoCD는 그것을 삭제하지 않는다 → GitOps만으로는 "선언되지 않은
  것이 없다"를 보장하지 못하는 사각지대가 남는다. 이걸 모르면 "prune 켰으니 클러스터 = Git"이라고
  착각하기 쉽고, 그게 루브릭이 지목한 흔한 오답이다.

### (c) `Application` 필요성 · 네임스페이스 3개 · argocd 파드 `Pending` — 부분 충족 (5/7)

**제출 요지**
> "c-1: 핵심 컴포넌트만 apply 하면 'argoCD의 기능을 수행할 수 있다'의 의미이고 Application은
> 어디서, 무엇을, 어디로 와 같은 상세 작업을 정의하는 것. c-2: 3개. 네임스페이스와 1:1 매핑이므로.
> c-3: 다시 apply 할 필요 없음."

**맞은 점**
- Application 필요성("어디서/무엇을/어디로"), 네임스페이스 3개 = Application 3개(1:1) 정확.
- c-3의 결론("재apply 불필요")도 정답 — 흔한 오답("실패했으니 다시 apply") 회피.

**놓친 점**
- c-3에서 문제가 요구한 **마스터/워커 역할 분담 근거**가 전무하다. 선언이 이미 컨트롤 플레인
  (etcd)에 등록되어 있으므로 워커 노드가 생기면 스케줄러가 알아서 배치한다는 설명이 있어야 만점.

## 문제 4. ArgoCD 퍼블릭 대시보드와 Ingress 분기 (32회차) — 9/14

### (a) **핵심** — ArgoCD 서버 Pod + Ingress + HTTPS 인증서 문제 — 부분 충족 (5/8)

**제출 요지**
> "1. 인증서로 복호화 하고 http로 보냄. 2. 스프링 서버 파드에서는 https 인증 처리가 되어있지
> 않았기 때문. 3. 암호문 그대로 넘기면 https 라우팅이 안됨. 4. 잘모르겠음."

**맞은 점**
- ①(Ingress에서 TLS 종료 후 HTTP 전달), ②(Spring Pod는 HTTPS 처리가 없어 평문 수신에 문제없음)
  정확.

**놓친 점**
- ③: "https 라우팅이 안 됨"은 문제 문장을 되풀이한 수준. **ArgoCD 서버 Pod는 내부적으로 HTTPS로
  동작해 암호문을 기대하는데, nginx 기반 Ingress는 암호문을 백엔드로 그대로 넘기는 HTTPS
  패스스루를 지원하지 않는다**는 두 사실의 충돌이 답의 뼈대다.
- ④ 미답(−2): `argocd-server` Deployment `args`에 **`--insecure`**를 추가해 Pod를 HTTP로 띄우며,
  사용자~Ingress 구간이 이미 HTTPS이므로 클러스터 내부 평문 구간은 실질 위협이 아니라는 판단까지가
  요구사항이었다.

### (b) 두 Ingress의 `ADDRESS` 동일 · 서브도메인 추가 — 부분 충족 (4/6)

**제출 요지**
> "하나의 로드밸런서와 하나의 ingress-controller로 요청받기때문... 서브도메인을 하나더 추가하면
> route53 -> LB -> ingress-controller 까지는 같고 ingress-controller에서 host를 확인하고
> ingress, service, pod를 새로 만들어야함."

**맞은 점**
- 동일 ADDRESS 이유(단일 LB + 단일 ingress-controller)와 host 기반 분기 흐름 정확 — 흔한 오답
  ("서브도메인마다 LB 추가")을 피함.

**놓친 점**
- 문제가 괄호로 명시한 "**Route 53 레코드와 인증서 포함**"을 놓쳤다. 정답 세트는 **Ingress 1 +
  해당 도메인용 Certificate(Secret) 1 + Route 53 A 레코드(별칭, 기존 NLB) 1** — HTTPS 인증은
  도메인 단위라 인증서는 재발급하되 ClusterIssuer는 재사용한다. "service, pod를 새로 만들어야
  함"은 새 앱이면 맞지만, 물어본 네트워킹 세트의 답은 아니다.

## 문제 5. 프로메테우스 · 노드 익스포터 · 그라파나 (33~34회차) — 10/18

### (a) 모니터링 대상 차이 · `DaemonSet` 이유 — 부분 충족 (3.5/5)

**제출 요지**
> "HPA, ArgoCD는 쿠버네티스 요소 상태, 프로메테우스/그라파나는 노드(ec2) 상태를 봄. DaemonSet으로
> 배포하는 이유는 모든 노드에 파드를 만들기 때문."

**맞은 점**
- 모니터링 대상 구분(쿠버네티스 요소 vs 노드 자체)은 정확.

**놓친 점**
- DaemonSet의 **동작**("모든 노드에 하나씩")만 쓰고, **왜 이 워크로드에 그게 필수인지**(각 노드의
  하드웨어 정보는 그 노드 안에서 수집해야 하는데 Deployment의 replicas는 스케줄 위치를 보장하지
  않음)를 연결하지 않았다 — 문제가 "워크로드의 성격과 함께"라고 명시한 부분.

### (b) **핵심** — Service 대신 `hostPort` · `__address__` `replace` — 부분 충족 (3/7)

**제출 요지**
> "서비스는 pod들 앞단에서 로드밸런싱 해주는 역할... 호출하는 쪽에서는 어느 파드가 응답했는지
> 중요하지 않다는 말이다. 하지만 노드 익스포터는 정확히 어떤 노드가 어떤 정보를 주었는지 정확히
> 알고있어야 함."

**맞은 점**
- "Service = 호출자가 어느 파드가 응답했는지 몰라도 되게 하는 추상화 vs 노드 익스포터 = 어떤
  노드의 데이터인지 정확히 알아야 함"이라는 대비는 루브릭의 라운드로빈 논거를 본질까지 파고든
  우수한 서술.

**놓친 점**
- 핵심 문항의 후반 두 요구가 미답(−4).
  ① **hostPort가 가능하게 하는 것**: 컨테이너 포트를 노드 자체 포트로 직접 노출 →
  `<노드IP>:9100`으로 각 파드에 직접 도달.
  ② **`__address__` 10250→9100 replace와의 쌍**: 프로메테우스 노드 자동 탐색의 기본 포트
  10250(주의: 노드 익스포터 포트가 아님)을 9100으로 바꿔 "노드가 9100을 연다 ↔ 프로메테우스가
  노드IP:9100으로 간다"로 양쪽을 맞춘 설계.

### (c) `readOnly` 마운트 · 그라파나 데이터 소스 URL — 부분 충족 (3.5/6)

**제출 요지**
> "컨테이너 정보가 아닌 노드(ec2) 자체 상태를 알고 싶기 때문. /proc: 메모리·CPU 사용량, 프로세스
> 목록 등, /sys: 하드웨어 정보, /: 디스크 사용량. readonly로 마운트 하는 이유: 읽기만 하면
> 되기때문."

**맞은 점**
- 호스트 경로 마운트 이유, `/proc`·`/sys`·`/` 세 경로의 정보 구분 모두 정확.

**놓친 점**
- **그라파나 데이터 소스 URL 문항 통째로 미답**(−2.5). `http://<프로메테우스 Service명>:9090`,
  같은 클러스터/네임스페이스에서 Service 이름 기반 내부 DNS로 도달 가능하다는 설명이 필요했다.
- readOnly 이유도 "읽기만 하면 됨"에 더해, 모니터링 도구가 호스트를 변경할 위험을 차단한다는
  보안 관점이 있으면 완결.

## 문제 6. 통합: 세 가지를 한꺼번에 켰을 때 (종합) — 미충족 (0/6)

**제출 요지**
> "잘 모르겠음."

**놓친 점**
- 미답이지만 아까운 지점: **재료는 이미 본인 답안에 다 있었다.** 1-c에서 "HPA가 Deployment
  replicas보다 우선"을, 3-b에서 "selfHeal은 클러스터가 Git과 다르면 Git 기준으로 되돌림"을
  정확히 썼다. 이 둘을 합치면 "피크에 HPA가 5대로 늘림 → ArgoCD가 Git(`replicas: 2`)과의 차이를
  감지해 되돌림 → **피크에 오히려 파드가 줄어드는** 충돌"이라는 결론이 나온다. 개별 규칙 암기와
  규칙 조합 추론 사이의 갭이 이번 답안의 가장 뚜렷한 약점.

## 복습 포인트

1. **규칙 조합 추론(문제 6)**: 개별 컴포넌트 규칙은 아는데 상호작용 시나리오에서 멈췄다.
   "이 두 컨트롤러가 같은 필드를 두고 싸우면 누가 이기나"류의 사고 훈련이 필요하다.
2. **IRSA 신뢰 정책의 `sub` 조건(2-b-5)**: OIDC 등록만으로는 "이 클러스터의 모든 Pod"에게 문이
   열린다. `sub` ↔ ServiceAccount ↔ `serviceAccountName` 3점 일치가 최소 권한의 실체이자 실무
   장애 1순위 지점 — 28~30회차 스크립트에서 다시 확인할 것.
3. **답안의 후반부 완주**: 4-a-④(`--insecure`), 4-b(인증서·Route 53), 5-b 후반(replace),
   5-c 후반(그라파나 URL), 3-b 후반(하지 않는 일) — 감점의 과반이 "문항의 뒷부분 미답"에서
   나왔다. 서술형 문제를 풀 때 질문을 문장 단위로 쪼개 각 절이 답변에 대응하는지 스스로 체크하는
   습관이 필요하다.
