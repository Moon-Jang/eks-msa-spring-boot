## 문제 1. 파드 오토스케일링 (S27)

### (a) 리소스 제한이 선행되어야 하는 이유

- 제한이 없으면 부하가 걸린 파드가 **노드(EC2)의 자원을 최대치까지 다 점유**한다.
- 그러면 옆에 파드를 늘릴 여유 자원이 없으므로 **파드 오토스케일 자체가 의미가 없다.**
- 그 상황에서 해야 할 것은 **EC2(노드) 오토스케일**이다.
- 반대로 노드 메모리 2GB / 파드 limit 500MB라면 파드를 4대까지 늘릴 수 있고, 그때 비로소 파드 스케일
  아웃이 의미를 갖는다.
- 감점: "성능상 권장사항" 정도로만 답하고 "왜 무의미해지는가"를 못 쓴 경우.

### (b) 세 요소의 역할 분담

| 요소 | 역할 |
| --- | --- |
| Deployment | 파드를 실제로 만들고 몇 대를 유지할지 결정 |
| HPA | 임계치·min/max 설정으로 판단해 **Deployment에게** 늘려라/줄여라 명령 |
| metrics-server | **파드의 실시간 리소스 사용량을 모니터링해 HPA에 보고** |

- **핵심**: HPA에는 **파드를 모니터링하는 기능이 없다.** 설정값만 들어 있고 실측은 metrics-server가 한다.
- metrics-server를 커스텀하지 않는 이유: 설치되면 **클러스터의 HPA를 알아서 찾아** 그 HPA가 관리하는
  파드를 모니터링하므로 우리 사정에 맞춰 바꿀 것이 없다. 반대로 HPA는 어떤 Deployment를 볼지·몇 대까지·
  임계치 얼마인지가 우리 사정이라 반드시 커스텀한다.
- 감점: HPA가 직접 CPU를 측정한다고 서술 → 이 문항 오답.

### (c) 값 설계 — 셋 다 반영되었는지 확인

값 자체는 정답 없음. 다음 3개가 근거로 들어가야 한다.

1. **지표의 정의**: `averageUtilization`은 **파드들의 평균 CPU 사용률**이다. 3대로 늘면 같은 총 부하가
   분산되어 파드당 평균이 내려가고(58%→43%), 임계치 아래로 떨어지면 더 늘릴 이유가 없다. **설정 오류가
   아니라 정상 동작**이며, 더 늘리려면 임계치를 낮추거나 더 강한 부하 도구가 필요하다.
2. **CPU 스파이크**: 파드 생성은 일종의 인프라 작업이라 **순간적으로 CPU를 많이 끌어다 쓴다.** 임계치가
   낮고 limit이 타이트하면 그 스파이크를 부하로 오인해 파드를 연쇄적으로 계속 만들 수 있다. 그래서
   **리소스를 넉넉히 잡거나, 임계치를 여유롭게 잡거나, 둘 다** 여유롭게 세팅한다.
3. **우선순위**: Deployment `replicas: 2` + HPA `minReplicas: 3`이면 **HPA가 우선**해 3대가 된다.
   혼선을 막기 위해 **둘을 맞춰 두는 것**이 좋다.

- 값 설계 참고: 실무 임계치는 **70~80%**가 적절(강의가 50%·30%로 낮춘 것은 순수 테스트 목적). 이 구분을
  하면 가점. `maxReplicas`를 노드 용량과 함께 고려했으면 가점.
- 감점: 임계치를 낮게 잡을수록 좋다고만 쓴 경우 / 3개 중 빠진 항목마다 부분 감점.

## 문제 2. 인스턴스 오토스케일링과 Pod 권한 (S28~S30)

### (a) Pending과 노드 관리 주체

- 파드가 계속 늘다가 **노드의 물리 자원 한계**에 도달하면 스케줄되지 못해 **`Pending`** 상태가 된다.
  파드는 실제 CPU·메모리를 점유하므로 노드가 감당 못하면 정상 실행되지 않는다.
- **노드그룹을 만들면 ASG가 생성되고, 노드(EC2)를 관리하는 주체는 EKS가 아니라 ASG다.** EKS는 ASG가
  만들어주는 노드를 빌려 쓰는 입장이다. (노드그룹을 편집하면 ASG 값도 함께 바뀐다.)
- cluster-autoscaler는 EKS 내 자원(특히 **자원 부족으로 Pending에 빠진 파드**)을 모니터링하다가 **ASG에
  노드 증감을 요청**하는 프로그램이다. "노드 수를 자동 조절한다"는 설명은 엄밀히 부정확하다 —
  **실제로 EC2를 만들고 없애는 주체는 ASG**다. ASG는 최대 N대까지 늘릴 능력이 있어도 **요청이 없으면
  늘려주지 않으므로** 이 요청 주체가 필요하다(이 문장까지 오면 가점).

### (b) Pod에 IAM 역할 부여 — 5단계

1. **엔터티 단위**: AWS는 EC2·RDS·S3·ASG·EKS 같은 **AWS 서비스(엔터티) 단위**로 역할을 부여한다. 그런데
   Pod는 AWS 서비스가 아니라 **EKS 안에서 돌아가는 쿠버네티스 요소**라 기본적으로 신뢰할 수 있는 엔터티가
   아니다. 그래서 "이 Pod는 신뢰할 수 있다"고 직접 등록해야 한다.
2. **OIDC 등록**: EKS 클러스터는 생성 시 **OpenID Connect 공급자 URL**을 발급받는다. EKS 자체가 AWS
   자원이므로 이 ID가 **EKS가 보증하는 신원**이 되고, IAM의 ID 제공업체로 등록하면 EKS 내부 요소가 AWS
   role을 사용할 길이 열린다.
3. **`sts.amazonaws.com`**: STS는 **보안 토큰 서비스**로 `AssumeRole`/`AssumeRoleWithWebIdentity` 같은
   **임시 보안 자격증명 발급**을 담당한다. 대상에 STS를 넣는 것은 "이 OIDC ID를 가진 주체는 STS를 통해
   역할 사용을 요청할 수 있다"는 설정이다.
4. **흐름**: Pod가 STS에 "나는 이 OIDC ID를 가진 신뢰할 수 있는 엔터티다, 역할을 쓰게 해달라" 요청 →
   STS가 임시 자격증명 발급(허용) → Pod가 그 역할로 **ASG에 EC2 증감 요청** → ASG가 EC2 증감.
5. **`sub` 조건**: 이 조건은 **kube-system의 `cluster-autoscaler` ServiceAccount를 쓰는 Pod만** 이 Role을
   assume하도록 제한한다. 없으면 **같은 클러스터(같은 OIDC)의 아무 Pod/ServiceAccount나** 이 역할을 써서
   EKS·ASG·EC2 권한을 갖게 되는 과도한 권한 문제가 생긴다.
   맞물리는 지점: Role은 **ServiceAccount의 `annotations`에 `eks.amazonaws.com/role-arn`**으로 연결하고
   Deployment가 `serviceAccountName`으로 그 SA를 쓴다. 따라서 **SA의 이름·네임스페이스가 `sub` 조건과
   정확히 일치해야** assume이 성공한다. (이 대응을 짚으면 큰 가점)
- 감점: STS를 단순 로그인 서비스로 서술 / "Pod에 그냥 역할을 붙이면 된다"는 답(1번 오답).

### (c) 핸즈온 3종

1. **Pending 진단**: `kubectl logs`는 무의미하다 — **프로그램이 아직 실행되지 않았다.** 자원이 부족해
   스케줄조차 못 됐으므로 애플리케이션 로그가 없다.
   → `kubectl describe pod <파드> -n <ns>`의 **Events**에서
   `0/N nodes are available: ... Insufficient memory, Insufficient cpu` 확인.
2. **설정 누락**: **노드그룹(=ASG)의 최대 크기가 2**였다. EKS → 컴퓨팅 → 노드 그룹 편집에서 최대 크기를
   3으로 상향해 해결. **ASG의 최대 용량이 절대 상한**이므로, HPA `maxReplicas`를 크게 잡아도 노드 상한에
   걸리면 파드는 Pending에 머문다(이 문장까지 오면 가점).
3. **비대칭**: 증설은 **부하 상황에 즉시 대처해야** 하므로 빠르고, 감축은 부하가 잠깐 사라졌다고 바로
   노드를 없애면 **다시 자원 부족 사태가 반복**될 수 있어 보수적으로 지연시킨다.
   가점: 이 서비스처럼 점심·저녁 피크가 두 번 있는 패턴에서 **안정성엔 유리(워밍 유지) / 비용엔 불리**
   라는 트레이드오프를 피크 간격 대비로 판단한 경우.

## 문제 3. ArgoCD GitOps (S31)

### (a) 확신 영역 구분 + 4인 팀의 문제

- **확신 가능: 소스코드/이미지.** GitHub Actions가 GitHub 소스를 기준으로 빌드해 ECR에 push하는 과정이
  자동화되어 있다.
- **확신 불가: k8s 매니페스트.** 워크플로우에 `apply` 스텝이 없고(`rollout restart`만) **매니페스트는
  개발자가 로컬에서 apply**하므로 클러스터 상태가 GitHub의 yaml과 같다고 보장할 수 없다.
- **안정성**: 팀이 합의한 구성이 아니라 개인이 임의로 자원을 바꾸거나 삭제할 수 있다. GitHub은 2대인데
  클러스터는 3대가 도는 등 실제 인프라가 합의와 어긋난 상태로 운영된다.
- **이력 관리**: 그런 변경이 **어디에도 기록에 남지 않아** 누가 언제 왜 바꿨는지 추적 불가.

### (b) prune / selfHeal + 하지 않는 일

- `prune: true` — **GitHub에서 삭제된 리소스를 클러스터에서도 자동 삭제.**
- `selfHeal: true` — **클러스터에서 수동 변경된 리소스를 GitHub의 원래 상태로 자동 복구.** 강의 표현대로
  "GitHub + ArgoCD로 이 아키텍처를 설계한 이유"에 해당하는 핵심 옵션.
- **하지 않는 일**: **GitHub에 선언되어 있지 않은 리소스를 누가 새로 만들었다고 해서 삭제하지는 않는다.**
- 사각지대: 누군가 GitHub에 없는 자원을 임의로 apply하면 **ArgoCD로는 잡히지 않고 그대로 살아남는다.**
  즉 GitOps만으로 "선언되지 않은 것이 없다"를 보장할 수 없어, kubectl 권한 통제나 리뷰 프로세스가 함께
  필요하다는 결론까지 가면 가점.
- 감점: `prune`이 이 사각지대를 해결한다는 답 → prune은 "GitHub에서 삭제된 것"에만 작동한다.

### (c) Application 자원 + Pending 후 재apply

- 필요한 이유: 인터넷의 install.yaml은 **기능만** 설치한다. ArgoCD는 어떤 저장소(`repoURL`)의 어떤
  브랜치(`targetRevision`)의 어떤 경로(`path`)를 어떤 네임스페이스(`destination.namespace`)와 맞출지
  모르므로 그것을 알려주는 선언이 필요하다.
- **네임스페이스 3개 → Application 3개.** Application 하나는 **한 개의 네임스페이스만** 바라본다.
- **재apply 필요 없다.** 자원에 대한 **선언은 이미 마스터 노드(컨트롤 플레인)에 등록**되어 있으므로, 노드만
  추가되면 마스터 노드가 "자원이 생겼으니 못 만들던 것을 만들어야겠다"고 판단해 워커 노드에 파드를 띄운다.
  가점: 같은 이유로 **실습 안 할 때 EC2를 꺼둬도** 다시 켜면 재apply 없이 복구된다는 언급 / **autoscaler가
  살아 있었다면 애초에 Pending 없이 자동 증설**됐을 것이라는 언급.
- 감점: "설치가 실패했으니 다시 apply해야 한다"는 답.

## 문제 4. ArgoCD 대시보드와 Ingress 분기 (S32)

### (a) HTTPS→HTTPS 문제 — 4요소 모두

1. Ingress는 사용자가 HTTPS로 보낸 **암호문을 복호화**한다. 암호화는 통신 구간에만 적용되고 백엔드로는
   평문이 전달된다.
2. 우리 **Spring 서버 Pod는 HTTPS 인증 처리가 되어 있지 않다.** 평문을 받을 준비가 된 서버였으므로 문제가
   없었다.
3. ArgoCD 서버 Pod는 **내부적으로 HTTPS로 동작**해 암호문을 받아 스스로 복호화할 준비를 한다. 하지만 우리
   Ingress는 **nginx 기반**이고 **암호문을 그대로 백엔드로 넘기는 HTTPS→HTTPS 라우팅을 지원하지 않는다.**
4. `argocd-server` Deployment의 컨테이너 `args`에 **`--insecure`** 한 줄을 추가해 Pod를 HTTP로 띄운다.
   위협이 되지 않는 이유: **사용자~Ingress 구간은 이미 HTTPS로 인증 처리되어 있고**, 그 뒤 내부 구간은
   이미 인증된 레벨이라 실질적 위협이 되지 않는다. Ingress는 Service의 **80**으로 보내고 80 → Pod 8080.
- 감점: `--insecure`만 쓰고 "왜 안전한지"(4번 후반) 누락 → 절반. 2번(Spring과의 차이) 누락 → 절반.
- 가점: 이 수정을 `apply`가 아니라 `kubectl edit deployment argocd-server -n argocd`로 한 이유(URL을 그대로
  apply했어서 로컬에 수정할 파일이 없다)와 저장 시 rollout이 일어난다는 언급.

### (b) 동일 ADDRESS와 도메인 분기

- ADDRESS는 **Ingress Controller 적용 시 생성된 (네트워크) 로드밸런서 주소**로, 두 Ingress가 같은
  ingress-controller/LB를 공유한다.
- 흐름: 사용자가 `argo.`로 들어옴 → Route 53이 LB로 라우팅 → **ingress-controller가 Host를 보고 어느
  Ingress 규칙인지 분기** → 그 Ingress가 지정한 Service(`argocd-server`) → Pod. `server.`면 같은 LB를 타고
  오더 시스템 Ingress → 오더 백엔드 Service → Spring Pod.
- 추가 시 필요한 것: **Ingress 1세트 + 그 도메인용 Certificate(Secret) 1세트 + Route 53 A 레코드(별칭,
  엔드포인트는 기존 네트워크 로드밸런서) 1개.** HTTPS 인증은 도메인 기반이라 **도메인마다 인증서를 따로**
  발급하고, `Certificate`의 `dnsName`은 Ingress의 `host`와, `secretName`은 `tls.secretName`과 일치해야
  한다. **ClusterIssuer는 재사용 가능.**
- 감점: 서브도메인마다 로드밸런서가 하나씩 더 필요하다는 답.

## 문제 5. 프로메테우스 · 노드 익스포터 · 그라파나 (S33~S34)

### (a) 모니터링 대상의 차이 + DaemonSet

- HPA(+metrics-server)와 ArgoCD로 본 것은 전부 **파드/쿠버네티스 자원 차원**(파드 CPU 점유율, 파드 개수,
  적용된 Service/Ingress/Deployment 현황)이었다. 프로메테우스/그라파나는 **노드(물리 컴퓨팅 자원) 차원**
  — 노드의 CPU·메모리·디스크·커널/하드웨어 상태를 본다. **한 번도 물리 자원을 모니터링한 적이 없었고**
  그것은 전문 프로그램의 도움이 필요한 영역이다.
- `DaemonSet`은 **클러스터 내 모든 노드에 파드를 하나씩 자동 배포**한다. 노드 익스포터는 **각 노드의
  하드웨어 정보를 그 노드 안에서** 수집해야 하므로, replicas로는 스케줄 위치가 보장되지 않는 Deployment가
  부적합하다. 가점: 노드가 오토스케일로 추가돼도 DaemonSet이 자동으로 따라붙는다는 언급.

### (b) hostPort — 핵심 문항

- Service를 쓰면 안 되는 이유: Service는 기본적으로 **라운드로빈으로 로드밸런싱**한다. 프로메테우스는
  **모든 노드 익스포터 파드 각각의 정보가 필요한데**, Service를 거치면 셋 중 하나로만 라우팅되어 특정
  파드의 데이터만 얻는다.
- `hostPort`: **컨테이너 포트를 노드 자체의 포트로 직접 노출.** 각 노드가 고유 IP를 갖고 있으므로
  `<노드IP>:9100`으로 그 노드의 파드에 직접 도달할 수 있다(Service 없이 고립을 면하는 수단).
- **쌍을 이루는 구조**: 프로메테우스는 노드 자동 탐색 시 노드에 붙은 `__address__` 라벨을 쓰고 **기본
  포트가 10250**이다. 10250으로는 노드 익스포터에 닿을 수 없으므로 정규표현식으로 `:10250`을 잡아
  **`:9100`으로 replace**한다. 즉 "노드 익스포터는 9100을 호스트 포트로 노출" ↔ "프로메테우스는
  노드IP:9100으로 찾아간다"로 양쪽 설정을 맞춘 것.
- 감점: hostPort를 NodePort Service와 혼동 / 라운드로빈 문제 누락 → 절반.

### (c) 볼륨 마운트 + 그라파나 연동

- 마운트 이유: 하드웨어/OS 정보는 **호스트의 리눅스 파일시스템에 쌓인다.** 반면 파드는 컨테이너로서
  **자기만의 OS와 파일 경로**를 가지므로, 호스트 경로를 컨테이너 내부(`/host/proc` 등)로 가져와야 노드
  익스포터가 읽을 수 있다.
- 경로별: **`/proc` = CPU·메모리·프로세스 실시간 정보**, **`/sys` = 커널(OS) 상태·디바이스/하드웨어**,
  **`/`(루트) = 디스크 사용량**. `readOnly: true`인 이유는 **읽기만 하면 되고**, 모니터링 도구가 호스트를
  변경할 위험을 차단하기 위함.
- 그라파나 연동: URL에 **`http://<프로메테우스 Service명>:9090`**(예: `http://prometheus-service:9090`).
  도달 가능한 이유: 둘 다 **같은 클러스터·같은 monitoring 네임스페이스의 파드**이고 프로메테우스 앞에
  **Service가 있으므로** 클러스터 내부 DNS로 Service 이름 + 포트만으로 통신할 수 있다.
- 가점: 대시보드는 Import → **템플릿 ID 1860**(Node Exporter, grafana.com URL의 고유 번호) 언급 /
  포트 3종(노드 익스포터 9100 · 프로메테우스 9090 · 그라파나 3000) 언급.

## 문제 6. 통합 (종합 추론)

### (a) HPA ↔ ArgoCD selfHeal 충돌

- 반드시 도출해야 할 결론: **HPA가 부하에 따라 파드를 5대로 늘려도, ArgoCD가 클러스터(5)와 GitHub(2)의
  차이를 감지해 GitHub 기준으로 되돌려버린다.** 즉 selfHeal이 HPA의 스케일 아웃을 취소해 **피크에 오히려
  파드가 줄어드는** 원하지 않는 동작이 발생한다.
- 근거 조합: (문제 1-c) HPA가 Deployment replicas보다 우선 + (문제 3-b) selfHeal은 클러스터가 GitHub과
  다르면 GitHub 기준으로 강제 복구.
- 부분 점수: "충돌한다"까지만 쓰고 어느 쪽이 이기는지/무엇이 문제인지 못 쓰면 절반.
- 가점: ArgoCD UI에서 **replicas 차이가 크리티컬한 OutOfSync**의 대표 예로 언급된 점(S32)을 끌어온 경우.
- `⚠ 강의 범위 밖` 가점: 매니페스트에서 `replicas` 제거해 HPA에 위임 / ArgoCD `ignoreDifferences`로
  `/spec/replicas` 무시. **몰라도 감점 없음.**

## 자주 나오는 오답 정리

1. **HPA가 직접 파드를 모니터링한다** → metrics-server의 역할(1-b).
2. **리소스 limit 없이도 HPA가 잘 동작한다** → 파드가 노드 자원을 독점해 무의미(1-a).
3. **Deployment replicas가 HPA minReplicas보다 우선** → HPA가 우선(1-c). 문제 6 추론이 무너진다.
4. **cluster-autoscaler가 직접 EC2를 만든다** → ASG가 만들고 autoscaler는 요청만(2-a).
5. **Pod에 IAM Role을 바로 붙일 수 있다** → Pod는 AWS 엔터티가 아니라 OIDC/STS 경유(2-b).
6. **Pending 파드를 `kubectl logs`로 진단** → 실행조차 안 됐으므로 `describe`(2-c).
7. **노드 추가 후 자원을 다시 apply해야 한다** → 선언은 마스터 노드에 이미 있음(3-c).
8. **prune이 "GitHub에 없는데 누가 만든 자원"도 지운다** → 지우지 않는다(3-b).
9. **Ingress가 HTTPS 패스스루를 지원한다** → nginx 기반에서 미지원, `--insecure`로 해결(4-a).
10. **노드 익스포터를 Service로 노출** → 라운드로빈 때문에 파드별 수집 불가, `hostPort`(5-b).
11. **10250이 노드 익스포터 포트다** → 프로메테우스의 노드 탐색 기본 포트, 9100으로 replace(5-b).
