## 문제 1. 파드 오토스케일링 (27회차) — 11.5 / 20

### (1-a) `resources` 선행 필수 이유 — 부분정답 (3.0/6)
- **맞은 점**: "HPA는 `resources.requests`를 기반으로 사용률을 계산한다" — 루브릭에는 없는 서술이지만
  실제 k8s 동작상 **정확하고 강의 서술보다 정밀한 근거**다. 타당한 근거로 인정해 부분점수 반영.
- **놓친 점**: 루브릭이 요구한 **용량 관점**이 빠졌다. dave의 근거는 "계산이 안 된다"(= 제어 불가)까지고,
  루브릭의 핵심은 "**자원 여유가 없어 무의미하다**"(= 스케줄 불가)라는 다른 층위다. limit이 없으면 부하받은
  파드 하나가 노드 자원을 최대치까지 점유하므로, 파드를 몇 대로 늘리라 지시해도 띄울 여유가 없다.
  반대로 노드 2GB / 파드 limit 500MB면 4대까지 패킹 가능하고, 그때 비로소 파드 스케일아웃이 의미를 갖는다.
- **미작성**("모르겠다") → 정답은 **노드(EC2) 오토스케일링**. 위 논리의 귀결로, 파드를 늘릴 여유가 없다면
  남은 선택지는 노드를 늘리는 것뿐이다. 이 대비가 문제 1에서 문제 2로 넘어가는 다리다.

### (1-b) HPA · Deployment · metrics-server 역할 구분 — 부분정답 (4.0/7)
- **맞은 점**: 세 요소의 역할 서술 자체는 방향이 맞다. 특히 metrics-server를 "파드 메트릭을 수집하고
  지속적으로 보고하는 역할"로 정확히 규정했다.
- **미작성**("모르겠다") → **HPA에 없는 기능은 파드를 모니터링(실측)하는 기능**이다. HPA는 임계치·min/max 같은
  **설정값 선언일 뿐**이고, 실제 파드 CPU/메모리 측정은 metrics-server가 해서 HPA에 보고한다.
  metrics-server 역할을 맞게 써놓고 이 답을 못 낸 것은 지식 부족보다 **역할 분담을 반대 방향에서 못 뒤집은 것**이다.
  → 실무 임팩트: 이 구분을 못 하면 metrics-server 미설치 클러스터에서 HPA 타깃이 `<unknown>`으로 멈추는
  가장 흔한 장애를 진단하지 못한다.
- **놓친 점**: 커스텀 불필요 이유의 핵심은 "설치되면 **클러스터의 HPA를 알아서 찾아** 그 대상 파드를 모니터링한다"는
  것이다. 우리 사정(어떤 Deployment/몇 대/임계치)은 전부 HPA 쪽에 있으므로 커스텀 지점도 HPA에만 있다.

### (1-c) 값 설계 3요소 — 부분정답 (4.5/7)
- **맞은 점**: ② 부트스트랩 CPU 스파이크를 부하로 오인하는 문제, ③ HPA 우선 + 실무에선 두 값을 맞춘다 — 둘 다 정확.
  특히 ③의 "HPA 우선" 전제는 문제 6의 정답을 도출하는 데 실제로 쓰였다.
- **놓친 점 1**: 문제가 `minReplicas`/`maxReplicas`/`averageUtilization`을 **정하라**고 했는데 **숫자가 없다**.
  값 자체에 정답은 없으나 제시가 요구사항이다. 실무 임계치는 70~80%가 적절하고 강의의 50%/30%는 테스트 목적이라는
  구분까지 붙으면 가점이었다.
- **놓친 점 2**: ①의 답이 "평균치가 내려갔다"에서 멈췄다. 요구된 것은 **지표의 정의**다 —
  `averageUtilization`은 파드들의 **평균** CPU 사용률이므로 총 부하가 3대로 분산되면 파드당 평균이 임계치
  아래로 떨어지고, HPA는 더 늘릴 이유가 없다. 즉 **설정 오류가 아니라 정상 동작**이라는 결론이 빠졌다.

## 문제 2. 인스턴스 오토스케일링 (28~29회차) — 17.0 / 22

### (2-a) Pending 원인과 ASG 관계 — 정답 (5.5/6)
- "EKS는 컨트롤 플레인만 관리하고 워커 증설은 ASG" → "autoscaler는 스케줄 불가 Pending 파드를 감지해
  ASG에 증설을 **요청**한다"로, 이 문항에서 루브릭이 가장 중요하게 보는 **"만드는 주체는 ASG, autoscaler는 요청자"**
  구분을 정확히 지켰다. 흔한 오답 4번(autoscaler가 직접 EC2를 생성한다)을 피했다.

### (2-b) IAM · OIDC · STS 5단계 — 부분정답 (5.0/9)
- **맞은 점**: `sub` 조건의 의도(특정 ServiceAccount로 한정)를 맞게 감지했다.
- **놓친 점 1**: 조건이 없으면 **같은 클러스터(같은 OIDC)의 아무 Pod/ServiceAccount나** 이 Role을 assume해
  ASG·EC2 권한을 갖는 **과도 권한** 문제가 생긴다는 결과 서술이 없다.
- **놓친 점 2**: 맞물리는 지점이 빠졌다 — **ServiceAccount의 `annotations: eks.amazonaws.com/role-arn`** +
  Deployment의 `serviceAccountName`이며, **SA의 이름·네임스페이스가 `sub` 문자열과 정확히 일치**해야 assume이 성공한다.
  → 실무 임팩트: IRSA 디버깅의 대부분이 이 문자열 불일치다. 이걸 모르면 `WebIdentityErr`를 만났을 때 볼 곳을 모른다.
- **놓친 점 3**: STS가 "임시 권한 주는 서비스"에서 멈췄다. `AssumeRoleWithWebIdentity`로 **OIDC 토큰을
  임시 자격증명과 교환**하는 것이고, 신뢰 정책 대상에 `sts.amazonaws.com`을 넣는 것은 "이 OIDC 신원의 주체는
  STS를 통해 역할 사용을 요청할 수 있다"는 선언이다.

### (2-c) 핸즈온 3종 — 정답 (6.5/7)
- 세 항목 모두 명확하다. `logs`가 무의미한 이유(컨테이너가 실행되기 전이라 애초에 로그가 없음) →
  `describe pod`의 Events에서 자원 부족 확인, 노드그룹 최대 크기 2 → 3 상향, 증설/감축의 비대칭 근거까지 전부 맞았다.
  흔한 오답 6번을 피했다.

## 문제 3. GitOps / ArgoCD (30~32회차) — 10.5 / 20

### (3-a) 확신 영역 / 불확신 영역 구분 — 부분정답 (3.5/7)
- **놓친 점 1**: 문제는 두 영역을 **구분**하라고 했는데 **확신 불가 영역만** 서술했다.
  확신 가능 영역은 **소스코드/이미지**다 — GitHub Actions가 GitHub 소스를 기준으로 빌드해 ECR에 push하는 경로가
  자동화되어 있기 때문이다. 확신 불가는 **k8s 매니페스트**이며, 근거는 워크플로우에 `apply` 스텝이 없고
  `rollout restart`만 있어서 매니페스트 적용이 로컬 수동이라는 점이다.
  → 이 **대조가 곧 ArgoCD 도입 명분**이므로, 한쪽만 쓰면 도입 근거가 서지 않는다.
- **놓친 점 2**: 안정성과 이력 관리의 분리가 흐리다. **안정성** = 팀 합의 구성이 아닌 상태로 인프라가 돌고
  (GitHub 2 vs 클러스터 3), 임의 변경·삭제가 가능하다. **이력** = 그 변경이 **어디에도 기록되지 않아**
  누가 언제 왜 바꿨는지 추적 불가하다. "임의로 수정했기 때문에 안정성이 떨어진다"는 순환 논리다.

### (3-b) prune / selfHeal 정의와 사각지대 — 부분정답 (4.0/7)
- **틀린 점**: 두 옵션의 **트리거가 어디인지**를 구분하지 못했다. 정확히는
  - `prune`: **GitHub에서 삭제된** 리소스를 클러스터에서도 삭제 (트리거 = Git 측 삭제)
  - `selfHeal`: **클러스터에서 수동 변경된** 리소스를 GitHub 상태로 자동 복구 (트리거 = 클러스터 측 드리프트)

  dave의 "prune은 deployment 변경사항 보고 삭제되는 게 있으면 삭제 / selfHeal은 싱크 맞추는 옵션"은
  두 트리거가 뭉개져 있다. **이 구분이 흐리면 문제 6의 "왜 HPA가 지는가"를 설명할 수 없다** — 결론은 맞혔지만
  그 근거를 여기서 확보하지 못한 셈이다.
- **맞은 점**: "GitHub에 없는 리소스는 체크/싱크하지 못한다"는 방향은 맞다.
- **놓친 점**: 그 귀결인 **사각지대 서술이 없다** — 누군가 GitHub에 없는 자원을 임의 apply하면 ArgoCD에
  잡히지 않고 그대로 살아남는다. 따라서 GitOps만으로 "선언되지 않은 것이 없다"를 보장할 수 없고,
  kubectl 권한 통제와 리뷰 프로세스가 함께 필요하다.

### (3-c) Application 자원과 재apply — 부분정답 (3.0/6)
- **결론은 맞고 근거가 틀렸다**: "네임스페이스 3개 → Application 3개"는 정답이지만, 이유를 "Application 하나가
  특정 **레포**를 바라보기 때문"으로 썼다. 실제 근거는 **Application 하나가 하나의 `destination.namespace`만
  바라보기 때문**이다. 같은 레포를 여러 Application이 각각 다른 path/namespace로 볼 수 있으므로,
  dave의 근거로는 3개가 도출되지 않는다. 우연히 맞은 답으로 보고 부분점수만 인정했다.
- **누락**: "**Application을 왜 따로 만들어야 하는가**"라는 앞부분이 통째로 빠졌다. 요지: 인터넷의 `install.yaml`은
  ArgoCD의 **기능만** 설치한다. 어떤 `repoURL`/`targetRevision`/`path`를 어떤 네임스페이스와 맞출지는
  ArgoCD가 알 수 없으므로, 그것을 알려주는 선언이 따로 필요하다.
- **근거가 얕은 곳**: 재apply 불필요는 맞지만 이유를 "마스터노드가 자동으로 상태를 바꿀 것"으로 썼다.
  핵심은 **선언(desired state)이 이미 컨트롤 플레인에 등록되어 있다**는 점이다 — 워커가 없어서 실행만 못 했던
  것이므로 노드가 생기면 스케줄러가 알아서 배치한다.

## 문제 4. HTTPS / Ingress 계층 (33회차) — 8.0 / 14

### (4-a) HTTPS → HTTPS 요구와 실제 구성 — 부분정답 (5.5/8)
- **맞은 점**: ①② 및 "HTTPS 패스스루는 안 된다"는 결론.
- **틀린 점 1 (방향이 반대)**: ④를 "ArgoCD가 복호화하는 옵션을 매니페스트에서 **제거**"로 썼다.
  실제로는 `argocd-server` Deployment 컨테이너 `args`에 **`--insecure` 한 줄을 추가**해 Pod를 HTTP로 띄운다.
  제거가 아니라 **추가**다.
- **누락**: 요구된 "**왜 보안 위협이 아닌지**"가 아예 빠졌다(루브릭상 절반 감점 항목).
  요지: 사용자~Ingress 구간은 이미 HTTPS로 암호화·인증되어 있고, 그 뒤는 클러스터 내부 구간이므로 실질 위협이 아니다.
  Ingress는 Service 80 → Pod 8080으로 보낸다.
- **틀린 점 2 (근거가 얕음)**: ③의 불가능한 이유를 "복호화한 걸 다시 암호화해서 못 넘긴다"로 썼는데,
  이는 메커니즘을 잘못 짚은 쪽이다. 정답은 "우리 Ingress가 **nginx 기반이고 HTTPS→HTTPS 패스스루 라우팅을
  지원하지 않는다**"는 **구현 제약**이다. 문제는 재암호화 실패가 아니라 패스스루 미지원이다.

### (4-b) 동일 ADDRESS와 도메인 분기 — 오답 (2.5/6)
- **누락 1**: 도메인 기반 분기 구조를 `ingress-controller → Ingress → Service → Pod` 흐름으로 설명하라는
  요구에 답하지 않았다. 핵심은 **ingress-controller가 Host 헤더를 보고 어느 Ingress 규칙인지 분기**한다는 것이다.
  두 Ingress가 같은 ADDRESS를 갖는 것은 둘 다 **같은 ingress-controller의 NLB를 가리키기 때문**이다.
- **누락 2**: 서브도메인 추가 시 "Route53 레코드와 인증서만"이라고 했는데 **Ingress 1세트가 빠졌다**.
  정답은 Ingress 1 + 해당 도메인용 Certificate/Secret 1 + Route 53 A(별칭, 기존 NLB) 1이며,
  `Certificate.dnsName` ↔ Ingress `host`, `secretName` ↔ `tls.secretName`이 일치해야 하고
  **ClusterIssuer는 재사용**한다.
- **맞은 점**: LB(NLB)는 늘어나지 않는다는 판단은 정확하다. 이 문항의 부분점수는 여기서 나왔다.

## 문제 5. 모니터링 (34회차) — 15.0 / 18

### (5-a) 모니터링 대상과 DaemonSet 선택 — 정답 (5.0/6)
- 노드 단위 지표 수집 대상과, 노드마다 정확히 하나씩 떠야 하므로 DaemonSet이라는 근거 모두 맞다.

### (5-b) hostPort와 포트 replace — 정답 (5.0/6)
- **이 문제의 핵심 문항을 통과했다.** Service의 **라운드로빈** 때문에 파드별 수집이 불가하다는 근거를 정확히 짚고,
  `hostPort`로 노드IP:9100에 직접 도달 → 프로메테우스 쪽 10250 → 9100 replace가 그 결정과 짝을 이룬다는
  대응까지 연결했다. 흔한 오답(Service로도 되지 않나?)을 피했다.

### (5-c) 마운트 경로와 그라파나 데이터소스 — 정답 (5.0/6)
- `/proc`·`/sys`·`/` 각 경로의 의미와, 데이터소스 `http://prometheus-service:9090` +
  클러스터 내부 Service DNS라는 근거가 맞다.

---

## 문제 6. 통합 추론 — HPA와 selfHeal의 충돌 — 정답 (5.5/6)

요구된 결론(HPA가 파드를 늘려도 selfHeal이 GitHub의 `replicas: 2`로 되돌려 **피크에 오히려 파드가 줄어든다**)을
정확히 도출했다. 이 답은 1-(c)의 "HPA 우선" 전제와 3-(b) selfHeal 동작을 **조합**해야 나오는데,
그 두 전제를 앞에서 확보해둔 덕에 논리가 성립했다.

- `⚠ 강의 범위 밖` (미시도, 감점 없음) → 해소 방법은 매니페스트에서 `spec.replicas`를 **제거**해 파드 수를
  HPA에 완전히 위임하거나, ArgoCD Application에 `ignoreDifferences`로 `/spec/replicas`를 무시하도록 선언하는 것이다.
  전자가 GitOps 원칙상 더 깔끔하다(선언되지 않은 필드는 다툴 일이 없다).

루브릭의 흔한 오답 11개 중 **명확히 밟은 것은 없다.** 9번(HTTPS 패스스루)은 "안 된다"를 맞췄으나 해결책의
방향이 반대(제거 vs 추가)였고, 3-(c)는 결론이 맞고 근거만 틀린 케이스다.
