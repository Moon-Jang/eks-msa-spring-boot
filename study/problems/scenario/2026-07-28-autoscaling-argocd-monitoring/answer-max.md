## 문제 1. 파드 오토스케일링 (27회차)

### (a) HPA 이전에 `resources` 선행이 필요한 이유

**묻는 것:** HPA를 붙이기 전 Deployment에 `resources` 제한이 반드시 선행돼야 하는 이유 · 리소스 제한이 없으면 파드 오토스케일이 무의미해지는 이유 · 그 상황에서 대신 해야 할 오토스케일링 종류(근거 포함).

**답:**

리소스 제한을 하지 않은 상태에서 트래픽을 많이 받거나 무거운 작업을 하게 되었을때 pod는 해당 ec2의 자원을 끝까지 할당하여 사용하기 때문에 pod를 늘릴수 있는 ec2 리소스 자체가 부족하기때문에 pod 오토스케일링이 의미가 없어진다. 그 상황에서는 pod 를 추가하는 방식이 아닌 노드(ec2)를 스케일 업 또는 스케일 아웃을 해야함.

### (b) HPA · Deployment · metrics-server 역할 구분

**묻는 것:** 세 요소의 역할 구분 · `HPA에 없는 기능`이 무엇이고 누가 대신하는지 · metrics-server를 커스텀할 필요가 없는 이유.

**답:**

HPA에 없는 기능은 모니터링과 파드를 직접 만들고 지우는 기능이 없음.

모니터링은 metric-server 가 파드의 CPU, 메모리 사용량을 수집해서 알려줌.

파드를 만들고 지우는 기능은 Deployment 가 replica 설정값을 통해 실제 파드 갯수를 유지함.

### (c) 이 주문 서비스의 HPA 값 설계와 근거

**묻는 것:** `minReplicas` / `maxReplicas` / `averageUtilization`을 정하고 근거 서술. 아래 셋이 모두 반영돼야 함.

- 임계치 50% 테스트에서 파드가 3대까지만 늘고 CPU가 43%로 내려간 이유(지표의 정의)
- "파드 생성 과정에서도 CPU가 튈 수 있으니 임계치와 리소스 limit을 여유롭게 세팅하라"의 의미
- Deployment `replicas` vs HPA `minReplicas`가 다를 때 무엇이 우선하는지 · 실무에서 둘을 어떻게 관리할지

**답:**

minReplicas: 2

maxReplicas: 4

averageUtilization: 70 or 80

c-1: HPA가 보는 값은 특정 파드의 사용률이 아니고 파드 전체의 평균 CPU 사용률이기 때문.

c-2: 파드가 새로 뜨면서 CPU를 사용하는데 특히 스프링부트를 실행시키는 초기에 CPU가 확 튐. 이때 불필요하게 파드를 또 증설하려고 하기때문.

c-3: HPA를 우선한다. 두 값이 다르면 혼동이 생길수 있기 때문에 동일하게 맞추는게 제일 좋다.

## 문제 2. 인스턴스 오토스케일링과 Pod 권한 (28~30회차)

### (a) HPA만 켠 상태에서 `maxReplicas`를 올리면

**묻는 것:** HPA만 적용된 상태에서 `maxReplicas`를 10·20으로 올려 부하를 계속 줄 때 발생하는 현상 · 그 원인과 파드가 놓이는 상태 · "노드를 관리하는 주체는 EKS가 아니다"의 의미 · cluster-autoscaler가 무엇을 감지해 누구에게 무엇을 요청하는 프로그램인지.

**답:**

maxReplicas를 10,20 으로 올려 부하를 계속 주면 발생하는 현상: 노드의 리소스가 허용될때 까지만 늘어나고 그 이후로는 pending 상태가 된다.

원인과 상태: HPA 는 파드가 몇개 필요한지만 알고 요청보내기 때문. 따라서 노드의 여유 리소스를 넘어가는 파드들은 pending 상태가됨.

"노드를 관리하는 주체는 EKS가 아니다"의 의미: AWS의 오토스케일링 그룹이 관리하기때문.

cluster-autoscaler가 무엇을 감지해 누구에게 무엇을 요청하는 프로그램인가 : 리소스 부족을 감지하여 오토스케일링그룹에 노드 수를 증가/감소 하라고 요청보내는 프로그램.

### (b) **핵심** — cluster-autoscaler Pod에 IAM 역할 부여가 복잡한 이유

**묻는 것:** 아래 흐름으로 설명.

- AWS가 역할을 부여하는 기본 단위(엔터티)는 무엇이고 왜 Pod는 그 단위가 아닌지
- EKS의 OpenID Connect 공급자 URL을 ID 제공업체로 등록하면 무엇이 가능해지는지
- 대상에 `sts.amazonaws.com`을 넣는 이유와 STS의 역할
- Pod → STS → 역할 → ASG 요청 흐름
- 신뢰 정책의 `"<OIDC>:sub": "system:serviceaccount:kube-system:cluster-autoscaler"` 조건이 없으면 생기는 문제 · 이 조건이 Deployment/ServiceAccount 설정의 무엇과 맞물리는지

**답:**

b-1: AWS에서 제공되는 리소스를 기본단위로 함. pod는 aws의 기본 리소스가 아니기 때문.

b-2: 역할부여가 가능해짐.

b-3: sts는 임시 보안자격증명을 발급하는 서비스. 

b-4: 클러스터 오토스케일러의 파드가 STS로 임시 보안자격증명을 요청. 요청이 승인되면 역할을 얻고 그 역할로 ASG에 EC2 증가/감소 요청을 보냄.

b-5: 잘 모르겠음.

### (c) **핸즈온** — 노드가 안 늘고 파드가 `Pending`

**묻는 것:**

- ① 이 파드 진단에 `kubectl logs`가 쓸모없는 이유 · 대신 쓸 명령과 확인할 내용
- ② 강의에서 실제로 발견한 **설정 누락**이 무엇이었고 어디서 고쳤는지
- ③ 노드 증설은 즉시, 감축은 10~30분 뒤인 비대칭이 의도된 설계인 이유

**답:**

1: pending 상태일땐 컨테이너가 아직 생성되지 않았기 때문에 logs 명령어가 쓸모가 없음. kubectl describe pod pod_name -n namespace 명령어로 확인

2: 오토스케일링 그룹의 최대값을 2 -> 3으로 수정

3: 증설은 새로 추가하는 것이라 서비스에 영향을 주는 부분이 없지만 감축은 진짜 필요 없는 노드가 맞는지 충분한 시간을 갖고 확인한 뒤 실행하는게 좋기때문.

## 문제 3. ArgoCD GitOps 도입 (31회차)

### (a) GitHub 소스 기준이라 확신 가능/불가능한 영역

**묻는 것:** 현재 아키텍처에서 "GitHub 소스 기준으로 돌고 있다고 확신할 수 있는 영역"과 "확신할 수 없는 영역" 구분 · 그 차이가 생기는 이유 · 팀원 4명이 모두 `kubectl` 권한을 가진 상태에서 누군가 로컬에서 `replicas: 3`으로 apply했을 때의 문제를 **안정성**과 **이력 관리** 관점으로 나눠 서술.

**답:**

확신할 수 있는 영역: github 액션에서 실행되는 구간. 소스코드 -> 이미지 빌드 -> ECR -> restart

확신할 수 없는 영역: 쿠버네티스 리소스 상태 및 설정 파일(yml) deployment, service, ingress 등등

차이가 생기는 이유: 팀원 개인이 git 을 거치지않고 쿠버네티스 리소스를 apply 해서 수정할 수 있기 때문

안정성 관점: 다른 팀원들은 깃헙에 있는 replicas 설정을 보고 리소스, 부하, 장애 대응 등의 판단을 할텐데 애초에 판단 근거 자체가 전부 틀려버려짐.

이력 관리 관점: 누가, 언제, 왜 바꿨는지 모름. 롤백도 쉽게 할 수 없음.

### (b) `prune: true` / `selfHeal: true` · ArgoCD가 하지 않는 일

**묻는 것:** 두 옵션이 각각 켜는 동작 구분 · 강의가 "첨언"으로 강조한 **ArgoCD가 하지 않는 일** 한 가지와 그것이 남기는 운영상 사각지대.

**답:**

prune: 깃에 없으면 클러스터에서도 없앰.

selfHeal: 깃에 선언된 리소스가 클러스터와 다르면 깃 설정으로 맞춤.

### (c) `Application` 자원의 필요성 · 네임스페이스 3개 · argocd 파드 `Pending`

**묻는 것:**

- ArgoCD 핵심 컴포넌트만 apply하면 부족해 `Application` 자원을 따로 만들어야 하는 이유
- 네임스페이스 3개를 운영하는 팀이면 Application이 몇 개 필요한지와 이유
- ArgoCD apply 직후 argocd 네임스페이스 파드가 `Pending`일 때, 노드를 추가한 뒤 실패한 자원을 다시 apply해야 하는가? · 마스터 노드와 워커 노드의 역할 분담으로 설명

**답:**

c-1: argoCD 핵심 컴포넌트만 apply 하면 "argoCD의 기능을 수행할 수 있다"의 의미이고 Application은 어디서, 무엇을, 어디로 와 같은 상세 작업을 정의하는 것.

c-2: 3개. Application 은 네임스페이스와 1:1 매핑이므로.

c-3: 다시 apply 할 필요 없음.

## 문제 4. ArgoCD 퍼블릭 대시보드와 Ingress 분기 (32회차)

### (a) **핵심** — ArgoCD 서버 Pod + Ingress + HTTPS 인증서 문제

**묻는 것:** 순서대로 서술.

- ① Ingress가 사용자 요청의 암호문에 대해 하는 일
- ② 우리 Spring 서버 Pod에서는 문제가 되지 않았던 이유
- ③ "암호문을 그대로 Pod에 넘기면 되지 않나" 대안이 불가능한 이유(Ingress 구현 기준)
- ④ 그래서 어떤 설정을 어디에 추가했고, 그것이 보안상 위협이 되지 않는 이유

**답:**

1. 인증서로 복호화 하고 http로 보냄.
2. 스프링 서버 파드에서는 https 인증 처리가 되어있지 않았기 때문.
3. 암호문 그대로 넘기면 https 라우팅이 안됨.
4. 잘모르겠음.

### (b) 두 Ingress의 `ADDRESS`가 같은 이유 · 도메인 기반 분기

**묻는 것:** `argo.<도메인>`과 `server.<도메인>` 두 Ingress의 `ADDRESS`가 동일한 이유 · 하나의 로드밸런서로 도메인 기반 분기가 이루어지는 구조를 ingress-controller → Ingress → Service → Pod 흐름으로 설명 · 서브도메인을 하나 더 추가하면 무엇을 몇 세트 더 만들어야 하는지(Route 53 레코드·인증서 포함).

**답:**

두 Ingress의 Address가 동일한 이유: 하나의 로드밸런서와 하나의 ingress-controller 로 요청받기때문.

서브도메인을 하나더 추가하면 route53 -> LB -> ingress-controller 까지는 같고 ingress-controller 에서 host 를 확인하고 ingress, service, pod 를 새로 만들어야함.

## 문제 5. 프로메테우스 · 노드 익스포터 · 그라파나 (33~34회차)

### (a) 모니터링 대상의 차이 · 노드 익스포터를 `DaemonSet`으로 배포하는 이유

**묻는 것:** HPA·ArgoCD로 봐 온 것과 프로메테우스/그라파나로 새로 보게 되는 것의 **모니터링 대상 차이** 구분 · 노드 익스포터를 `Deployment`가 아니라 `DaemonSet`으로 배포하는 이유(이 워크로드의 성격과 함께).

**답:**

HPA, ArgoCD는 쿠버네티스 요소 상태, 프로메테우스/그라파나는 노드(ec2) 상태를 봄. DaemonSet으로 배포하는 이유는 모든 노드에 파드를 만들기 때문.

### (b) **핵심** — Service 대신 `hostPort` · `__address__` 포트 `replace`

**묻는 것:** 노드 익스포터에 Service를 쓰면 안 되는 이유를 **Service의 기본 동작 방식**을 근거로 설명 · `hostPort`가 무엇을 가능하게 하는지 · 프로메테우스 config에서 `__address__` 라벨의 기본 포트 `10250`을 `9100`으로 `replace`하는 설정이 이 결정과 어떻게 **쌍을 이루는지**.

**답:**

서비스는 pod 들 앞단에서 로드밸런싱 해주는 역할을 한다. 그말인 즉 pod가 1개던 여러개던 호출하는 쪽에서는 어느 파드가 응답했는지 중요하지 않다는 말이다. 하지만 노드 익스포터는 정확히 어떤 노드가 어떤 정보를 주었는지 정확히 알고있어야 함.


### (c) `/proc`·`/sys`·`/` `readOnly` 마운트 · 그라파나 데이터 소스 URL

**묻는 것:** 세 경로를 `readOnly`로 마운트하는 이유(파드는 자기만의 파일 경로를 갖는데 왜 호스트 경로를 가져와야 하는지 · 세 경로가 각각 담는 정보) · 그라파나 데이터 소스 URL에 무엇을 입력하는지(포트 포함) · 그라파나가 그 주소로 프로메테우스에 도달할 수 있는 이유.

**답:**

파드는 자기만의 파일 경로를 갖는데 왜 호스트 경로를 가져와야 하는지: 컨테이너 정보가 아닌 노드(ec2) 자체 상태를 알고 싶기 때문.

세 경로가 각각 담는 정보: /proc: 메모리 사용량, CPU 사용량, 프로세스 목록 등, /sys: 하드웨어 정보, /: 디스크 사용량

readonly 로 마운트 하는 이유: 읽기만 하면 되기때문.

**묻는 것:** 강의에서 배운 **각 자원의 동작 규칙만으로** 추론해, 어느 쪽이 이기고 그 결과 피크에 무슨 일이 생기는지까지 서술. (+ ⚠ 범위 밖: 이 충돌을 해소하는 실무적 방법(매니페스트에서 `replicas` 제거, ArgoCD가 특정 필드 차이를 무시하도록 설정 등) / 몰라도 됨)

잘 모르겠음.
