## 문제 1. 인프라 자원 사전 준비

### (1-a) RDS 3306 / Public Access — 부분정답
- **맞은 점**: mysql 3306을 인바운드에 열어 EC2/Pod가 RDS에 접근하게 해야 한다는 방향성.
- **틀린/놓친 점**: 문제가 명시적으로 요구한 **Public Access를 별도 허용해야 하는 이유**를 안 다룸.
  AWS 내부는 포트만 열면 이미 접근 가능하지만, **로컬 PC의 DB 툴 등 AWS 바깥**에서 스키마 작업할 일이
  있어 Public Access가 필요하다는 "AWS 내부 vs 외부" 대비가 핵심인데 통째로 빠짐. 포트도 3360 오타(→3306).

### (1-b) Redis ClusterIP — 부분정답
- **맞은 점**: Ingress는 외부 통신용이고 Redis는 내부 전용이라 노출 안 함 — 정확.
- **틀린/놓친 점**: Service 경유 이유를 "장애 파드 감지 후 정상 파드로만 라우팅"이라 했으나, 루브릭의 핵심은
  **Pod IP가 재생성마다 바뀌므로 안정적인 이름(Service DNS)으로 라우팅**한다는 점. 단일 Redis 파드 구성에서는
  페일오버 논리가 성립하기 어렵고, 핵심 근거(Pod IP 휘발성)를 놓침.

### (1-c) 일회성 vs 반복 — 정답
- 인프라는 한 번 만들어 지속 사용, CI/CD는 반복 성격. 루브릭과 일치.

## 문제 3. Secret 운영 / 자격증명

### (3-a) Secret 생성 명령 / base64 — 부분정답
- **놓친 점**: 명령에 **DB_HOST 키가 누락**됨(`--from-literal=DB_PW`만 있음). 문제는 두 키를 요구.
- **절반 맞음**: base64라고 답했으나 **"암호화가 아니라 디코딩 가능한 인코딩"**이라는 핵심 뉘앙스를 못 박음.

### (3-b) JWT_SECRET 추가 절차 — 정답
- 키 추가 전용 명령이 없어 **삭제 후 재생성**, env 이름과 yaml 변수명 일치 — 핵심 두 축 모두 포함.
  (secretKeyRef.key와 변수명을 DB_HOST 예시로 뭉뚱그린 점은 사소한 불명확성)

### (3-c) GitHub Secrets AWS 키 위험 — 부분정답
- **맞은 점**: 계정 해킹 시 키 노출 가능성 언급.
- **놓친 점**: 루브릭 핵심인 **장기(long-lived) 자격증명이라 유출 시 만료 전까지 계속 악용, 수동 로테이션 부담,
  어드민 키면 계정 전체 위험**을 못 짚음. 답변에 물음표가 붙어 확신도 낮음.
- 범위 밖(가점) OIDC/IAM Role: 미시도 → 가점 없음(감점 아님).

## 문제 4. 무중단 배포 / 트러블슈팅

### (4-a) readinessProbe — 정답
- 부팅 시간 확보, 정상 응답 확인 후 기존 파드 유지 → 가용성 보장이라는 취지 충족.

### (4-b) resources requests/limits — 부분정답
- **놓친 점 1**: 미설정 시 핵심 문제는 **한 파드가 노드 자원을 독점해 다른 파드가 기아 상태**가 되는 것.
  dave는 "오토스케일링이 자원 초과 생성 → 노드 OOM"으로 설명했는데 인과가 루브릭과 어긋남
  (requests/limits 미설정과 HPA는 별개 축).
- **놓친 점 2**: 이 문제의 핵심인 **limits를 requests보다 여유 있게 잡아 피크 버스트 여지 확보**
  (예: req 0.5/250Mi, limit 1/500Mi)를 제시 못 함. 흔한 오답(두 값 동일)에 가까운 방향.

### (4-c) revisionHistoryLimit — 정답
- 트레이드오프(리비전이 적으면 롤백 범위 축소)를 정확히 짚음. 낮추는 이유는 일반론이나 수용 가능.

### (4-d) 핸즈온 Running 0/1 — 부분정답
- **맞은 점**: `get pods → describe → logs` 명령 순서 자체는 정확.
- **놓친 점**: 요구된 **강의 원인 패턴(스키마 오타 → DB 연결 실패, unknown database) 설명**과
  **readinessProbe가 없었다면 미준비 파드가 Ready로 오인돼 기존 정상 파드가 먼저 내려가 다운타임**이라는
  서술이 전혀 없음. 명령만 나열해 서술형 요구를 절반만 충족.

## 문제 5. HTTPS 인증서

### (5-a) 비대칭키 이유 — 정답
- 공개키는 배포, 개인키는 서버 보관이라 다수에게 뿌려도 안전 — 핵심 충족.
  (대칭키가 왜 구조적으로 불가한지까지 대비했으면 완벽)

### (5-b) 인증서 발급 흐름 — 오답
- **틀림**: "CA로부터 공개키/비밀키를 발급받는다"는 서술은 부정확.
- **올바른 설명**: **서버가 키쌍을 직접 생성 → CSR(공개키+도메인) 작성 → CA 제출 → CA 도메인 소유권 검증
  → 서명·발급.** CSR도, CA 검증도 빠졌고 키 생성 주체가 뒤바뀜.

### (5-c) cert-manager / ClusterIssuer / Certificate — 부분정답
- ClusterIssuer 역할만 서술(정확). **Certificate(도메인 정보로 발급 요청)** 와
  **cert-manager(실제 CA 요청·발급·Secret 저장 수행)** 두 자원 설명 누락. 3개 중 1개.

### (5-d) Ready=False 원인 — 정답
- Ingress 라우팅부터 의심(외부 접근 가능 여부 확인) — 루브릭 핵심(CA의 도메인 검증 HTTP 요청을 받을
  http 라우팅 선행)과 일치.

## 총평

**강점**
- 문제 2 전체와 개념 구분형(4-a, 4-c, 5-d, 6-a)에서 안정적. profile 분기, Secret 주입 시점, readinessProbe 취지,
  revisionHistoryLimit 트레이드오프, Certificate Ready=False의 Ingress 선행 조건까지 핵심을 정확히 짚음.
- 흔한 오답 함정(JWT "덜 중요해서", Secret "암호화")에는 빠지지 않음.

**보완할 점 (실무 임팩트 순)**
1. **서술형 요구를 명령/키워드로만 답하는 경향** — 4-d가 대표적. 명령 순서는 맞지만 "원인 패턴 설명"과
   "probe 부재 시 다운타임 시나리오"라는 서술 요구를 놓쳐 만점을 못 받음. "~을 서술하라"면 근거·인과·결과까지
   문장으로 마무리할 것.
2. **핵심 대비(contrast)를 빠뜨림** — 1-a의 "AWS 내부 vs 외부(Public Access)", 4-b의 "requests < limits 버스트"가
   각 문제의 채점 포인트인데 통째로 누락. 트레이드오프/대비가 질문의 뼈대인 경우가 많다는 점 유의.
3. **정확성 흠결** — 5-b는 방향 자체가 틀림(서버가 키쌍을 만들고 CSR을 CA에 제출·검증받는 구조를 "CA가 키를 발급"으로
   역전). 3-a 명령의 DB_HOST 누락, "인코딩 ≠ 암호화" 미언급도 정확도 문제.
4. **모르는 항목 방치** — 6-c는 강의 범위 안 필수 요소(`kubectl apply` 스텝 추가)인데 미해결. 범위 밖 가점
   (OIDC, Blue-Green)은 안 해도 되지만, 범위 안 필수는 채워야 함.

## 복습 1. RDS 접근 경로 — 내부 vs 외부 (원 1-a)
같은 VPC 안의 EKS Pod가 RDS에 붙는 경우와, 네 **로컬 PC의 DB 툴**(DBeaver 등)로 RDS에 붙어 스키마 작업을
하는 경우를 비교하라.
- (a) 두 경우 각각 RDS 보안그룹 인바운드에 열어야 하는 포트 번호는?
- (b) 포트만 열면 되는 쪽과, 포트 외에 **Public Access까지** 켜야 하는 쪽은 각각 어디이고 그 이유는?
- (c) "같은 AWS 내부 접근"과 "AWS 바깥 접근"이 네트워크 도달 관점에서 무엇이 다른지 한 문장으로.

**답:**

a - 3306 포트 mysql 기본포트임 이건
b - 포트만 여는건 RDS가 VPC내에 있고 내부망에 있을시 퍼블릭 액세스없이 내부망 포트를 열어주면 된다. 다만 퍼블릭 액세스는 실제 운영관점에서 같은 VPC 대역이 아니거나 외부에서 접근해 DB 운영 관리를 해야할때 외부접근을 열어준다고하는데 사실 RDS를 쓰는거면 같은 VPC에 VPN으로 내부망에 접근해서 관리하는게 베스트라고 생각한다.
c - 같은 AWS 내부 접근 (같은 VPC) 면 내부망에서 통신이 가능해 빠르지만 외부 접근이면 물리적인 거리에따라 레이턴시가 늘어날 것이다.

## 복습 2. Service를 거치는 진짜 이유 (원 1-b)
Spring Pod가 Redis에 붙을 때 Redis **Pod IP를 직접** 설정하지 않고 `Service` 이름으로 접속한다.
- (a) Redis Pod가 죽고 재생성되면 Pod IP는 어떻게 되는가? 그때 Pod IP를 직접 박아뒀다면 무슨 일이 생기나?
- (b) Service(ClusterIP)가 이 문제를 어떻게 해결하는지 "안정적인 이름/DNS" 관점에서 서술하라.
- (c) (함정 점검) "특정 Redis 파드에 장애가 나면 Service가 정상 파드로만 라우팅한다"는 설명이 **단일 Redis
  파드** 구성에서 성립하는가? 성립하지 않는다면 그 논리가 언제(어떤 구성에서) 유효해지는지 서술하라.

**답:**

a. 해당 POD IP는 교체된다. 파드 IP 를 직접 박았다면 레디스 연결이 안되기때문에 관련 시스템 장애가 발생한다.
b. 인그레스가 서비스로 라우팅하면 서비스는 새로 교체된 IP를 다시 등록해서 서비스로 연결시 정상 파드로만 라우팅하기 때문에 안정적이다.
c. 단일 레디스 파드일때도 특정 파드가 고장나면 마스터노드에서 파드 상태를 모두 감시하고 복구해주기 때문에 성립한다. 언제 성립안하는지는 모르겟다.
